# Version 0.1 Specification

This document converts the research explanation into an implementation-oriented contract for the first prototype. It is intended to be directly translatable into schemas, fixtures, validation rules, and regression tests.

## 1. Constitutional research constraints

These constraints are normative requirements for every v0.1 component. They should be represented as testable assertions against system behavior, not as aspirational prose.

| ID | Constraint | Implementation requirement | Failure mode to test |
| --- | --- | --- | --- |
| CRC-001 | The system must not equate openness with randomness. | A preserved remainder must remain connected to shared anchors and an explicit path. Random divergence, generic association, or ungrounded plurality must be rejected or rolled back. | The system labels arbitrary continuations as “open” without anchor or path evidence. |
| CRC-002 | The system must not equate verbosity with depth. | Longer output must not increase depth or aptness classification unless it exposes stronger anchors, paths, tensions, evidence, or legitimate remainders. | The system rewards expanded paraphrase or decorative prose as deeper than a compact apt expression. |
| CRC-003 | The system must not preserve ambiguity where evidence should resolve a consequential factual question. | When stakes are material and the unresolvedness is epistemic insufficiency, the closure regulator must investigate, request evidence, or suspend judgment rather than preserve ambiguity. | The system treats a factual dispute as perspectival or generatively open when relevant evidence is available or required. |
| CRC-004 | The LLM must not be the authoritative epistemic state. | LLM generations may propose parses, claims, interpretations, or renderings, but accepted state must live in auditable typed objects with provenance, dependencies, and closure decisions. | A fluent generated answer is accepted without anchors, evidence, assumptions, or revision path. |

## 2. Core ontology

All v0.1 implementations should model the inquiry as typed state. Natural-language output is a rendering of this state, not the state itself.

### 2.1 `Inquiry`

Represents the object currently being explored.

Required fields:

```yaml
id: string
signal_or_question: string
explicit_context: string | null
domain: string
purpose: string
stakes: low | medium | high | critical
requested_action: answer | interpret | investigate | compare | create | decide | explore
closure_policy: resolve | preserve_open | investigate_first | contrast | ask_user | auto
available_resources: string[]
```

Validation rules:

* `signal_or_question` must be non-empty.
* `stakes` must influence closure decisions.
* `closure_policy` may be user-specified, but it cannot override constitutional constraints.

### 2.2 `Anchor`

Represents a constraint that grounds the inquiry.

Required fields:

```yaml
id: string
type: linguistic_convention | observed_fact | source | domain_rule | user_context | declared_value | accepted_claim
content: string
provenance: string
strength: weak | moderate | strong
```

Validation rules:

* Every accepted `Claim`, `Interpretation`, and `Path` transition must reference at least one anchor.
* User-inferred context must not be recorded as lived experience unless explicitly supplied by the user.

### 2.3 `Claim`

Represents a proposition with revision conditions.

Required fields:

```yaml
id: string
proposition: string
grounds: string[]
sources: string[]
assumptions: string[]
scope: string
dependencies: string[]
counterevidence: string[]
uncertainty: low | medium | high | unresolved
revision_history: string[]
status: proposed | accepted | challenged | retracted | suspended
```

Validation rules:

* Factual claims require grounds or must remain `proposed`/`suspended`.
* Accepted claims must expose assumptions and revision conditions.

### 2.4 `Interpretation`

Represents a possible understanding of a signal.

Required fields:

```yaml
id: string
signal_ref: string
reading: string
fidelity_to_signal: weak | moderate | strong
contextual_fit: weak | moderate | strong
relational_continuity: weak | moderate | strong
explanatory_power: weak | moderate | strong
horizon_or_perspective: string | null
alternatives: string[]
status: proposed | retained | rejected | human_owned
```

Validation rules:

* An interpretation must not be treated as a factual claim unless converted into a `Claim` with grounds.
* Multiple retained interpretations may be valid under semantic ambiguity, normative plurality, or generative openness.

### 2.5 `Path`

Represents locally connected movement through claims or interpretations.

Required fields:

```yaml
id: string
start_anchor_ids: string[]
steps:
  - from: string
    to: string
    transition_reason: string
    continuity_profile:
      referential: pass | fail | not_applicable
      relational: pass | fail | not_applicable
      pragmatic: pass | fail | not_applicable
      causal_or_argumentative: pass | fail | not_applicable
      thematic: pass | fail | not_applicable
      contextual: pass | fail | not_applicable
      tonal: pass | fail | not_applicable
      cue_dependence: pass | fail | not_applicable
      novelty: low | medium | high
rollback_points: string[]
status: active | complete | rolled_back | drift_detected
```

Validation rules:

* A path with failed cue dependence must not support generative openness.
* Drift must trigger rollback or rejection rather than decorative continuation.

### 2.6 `Tension`

Represents a currently unharmonized relation.

Required fields:

```yaml
id: string
type: contradiction | competing_value | incompatible_interpretation | unresolved_assumption | evidence_conflict
items: string[]
description: string
severity: low | medium | high
resolution_options: investigate | disambiguate | contrast | suspend | rollback | ask_user
```

Validation rules:

* Contradictions and evidence conflicts in consequential factual matters should route toward investigation or suspension.
* Competing values should route toward contrast unless the user has supplied a governing value or decision procedure.

### 2.7 `Remainder`

Represents content left unresolved, with its reason typed.

Required fields:

```yaml
id: string
type: evidence_gap | ambiguity | pluralism | open_question | generative_remainder
content: string
belongs_to: system | human | shared | external_evidence
preservation_reason: string
resolution_conditions: string[]
```

Validation rules:

* `generative_remainder` must have a shared anchor and a non-arbitrary path.
* `evidence_gap` must not be presented as productive openness when stakes require investigation.

### 2.8 `DecisionState`

Represents the system's current closure posture.

Required fields:

```yaml
id: string
state: resolve | continue | investigate | contrast | suspend | rollback | preserve_openness | ask_user | transfer_to_human
reason: string
unresolvedness_type: incoherence | epistemic_insufficiency | semantic_ambiguity | perspectival_or_normative_plurality | generative_openness | none
next_actions: string[]
stopping_condition: sufficient_resolution | insufficient_evidence | value_conflict | generative_openness | resource_limit | incoherence | human_judgment_required
```

Validation rules:

* `state` must match the closure-state taxonomy and the inquiry stakes.
* `preserve_openness` is invalid for unresolved consequential factual claims.

## 3. Closure-state taxonomy

| Closure state | Definition | Required operation | Valid terminal decisions | Invalid behavior |
| --- | --- | --- | --- | --- |
| Incoherence | No stable shared interpretation exists under the current context. | Reject, repair, ask for context, or assess broader speech act. | `rollback`, `suspend`, `transfer_to_human` | Inventing coherence from fluent association. |
| Epistemic insufficiency | The question has an answer, but evidence is missing or inadequate. | Investigate, request evidence, compare sources, or suspend. | `investigate`, `suspend`, `resolve` only after support improves | Treating factual uncertainty as legitimate plurality. |
| Semantic ambiguity | Several meanings are possible because the signal is unclear. | Disambiguate, ask a clarifying question, or retain alternatives. | `continue`, `contrast`, `transfer_to_human` | Choosing one meaning silently when it affects outcome. |
| Perspectival or normative plurality | Several positions remain legitimate under different commitments, values, or horizons. | Contrast positions and expose assumptions. | `contrast`, `transfer_to_human`, `suspend` | Treating value disagreement as empirical error or arbitrary preference. |
| Generative openness | A shared anchor exists, but completion appropriately belongs partly to the receiver. | Preserve the remainder and mark human-owned completion. | `preserve_openness`, `transfer_to_human` | Exhaustive paraphrase, random continuation, or one canonical interpretation. |

## 4. Version 0.1 system contract

### 4.1 Input contract

A v0.1 request must compile into the following fields:

```yaml
signal_or_question: string
explicit_context: string | null
domain: factual | historical | normative | textual | artistic | creative | mixed
purpose: answer | explanation | interpretation | decision_support | exploration | creation | evaluation
stakes: low | medium | high | critical
```

Compiler requirements:

* Preserve the user's exact `signal_or_question`.
* Separate explicit context from inferred context.
* Mark inferred domain and purpose as assumptions when not supplied.
* Escalate closure strictness as `stakes` increase.

### 4.2 Output contract: Inquiry Packet

A v0.1 response must produce an Inquiry Packet with these fields:

```yaml
inquiry_type: string
shared_anchors: Anchor[]
current_claims: Claim[]
interpretive_path: Path[]
evidence_and_assumptions:
  evidence: string[]
  assumptions: string[]
tensions_or_counterpositions: Tension[]
type_of_unresolvedness: DecisionState.unresolvedness_type
closure_decision: DecisionState
generative_remainder: Remainder | null
human_facing_rendering: string
```

Packet-level validation rules:

* `human_facing_rendering` must be derivable from the packet.
* Any evidence-dependent claim in `human_facing_rendering` must appear in `current_claims`.
* Any unresolved issue in `human_facing_rendering` must appear in `tensions_or_counterpositions`, `generative_remainder`, or `closure_decision`.
* The packet must distinguish system contribution from human-owned completion.

## 5. Success and failure tests

The following fixtures should become regression tests for schemas, closure decisions, and rendering behavior.

### 5.1 `justice`

Input:

```yaml
signal_or_question: "justice"
explicit_context: null
domain: normative
purpose: exploration
stakes: medium
```

Expected success:

* Shared anchors include fairness, legitimacy, treatment, and social order.
* Interpretive paths may move through virtue, institutions, equality, desert, repair, or responsibility if transitions are locally grounded.
* The system does not claim to exhaust the concept.
* Factual subclaims route to `epistemic_insufficiency` when evidence is missing.
* Normative disagreement routes to `perspectival_or_normative_plurality` and `contrast`.

Failure examples:

* Produces a single final definition as if no legitimate plurality remains.
* Treats all justice-related disagreement as factual uncertainty.
* Invents a user's personal theory of justice without explicit context.

### 5.2 `The city breathed`

Input:

```yaml
signal_or_question: "The city breathed"
explicit_context: null
domain: textual
purpose: interpretation
stakes: low
```

Expected success:

* Shared anchors include city, organic life, rhythm, collective movement, or atmosphere.
* The path may retain several coherent readings, such as crowds, traffic, weather, nightlife, or urban vitality.
* Closure decision is `preserve_openness` when the path remains coherent and non-arbitrary.
* The rendering stops before replacing the sentence with one definitive paraphrase.

Failure examples:

* Explains the sentence only as “the city had lungs,” unless literalism is contextually requested.
* Adds unrelated associations that would fit many other prompts equally well.
* Produces an exhaustive paraphrase that collapses the generative remainder.

### 5.3 `The city was big`

Input:

```yaml
signal_or_question: "The city was big"
explicit_context: null
domain: textual
purpose: interpretation
stakes: low
```

Expected success:

* Shared anchor identifies ordinary size or scale.
* Closure decision is `resolve` or minimal `continue` because little productive remainder is present by default.
* The rendering remains concise and does not manufacture depth from flat description.

Failure examples:

* Treats ordinary vagueness about exact size as profound openness.
* Generates elaborate symbolic readings without contextual anchors.
* Scores the statement as deeper because the explanation is longer.

### 5.4 `Colorless green ideas sleep furiously`

Input:

```yaml
signal_or_question: "Colorless green ideas sleep furiously"
explicit_context: null
domain: textual
purpose: interpretation
stakes: low
```

Expected success:

* Initial sentence-level semantics may be marked as incoherent or resistant to literal scene construction.
* The system checks whether broader context changes the speech act.
* With syntax, surrealism, poetry, or language-philosophy context, the sentence can have a clear function even when the literal scene remains incoherent.
* Closure decision may be `suspend`, `ask_user`, `contrast`, or contextually bounded `preserve_openness` depending on supplied context.

Failure examples:

* Declares the sentence simply meaningless in all contexts.
* Treats the literal impossibility as a factual contradiction requiring external evidence.
* Invents a stable literal scene and accepts it as a grounded interpretation.

## 6. Minimum implementation checklist

Before a v0.1 prototype is considered compliant, it must support:

* A serializable Inquiry Packet schema.
* Validation that every accepted claim or interpretation has anchors.
* A closure classifier over the five closure states.
* Rule-based routing from closure state to `DecisionState`.
* Fixture tests for the four examples above.
* Tests proving that generated language cannot directly overwrite typed inquiry state.
